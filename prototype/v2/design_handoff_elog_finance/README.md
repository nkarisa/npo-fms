# Handoff: ELOG Finance Management System

## Overview

A finance and grant management system for a Kenyan non-profit (ELOG) operating on donor-restricted
funds. The system replaces spreadsheet-based bookkeeping with a double-entry general ledger that is
fund-aware and programme-aware, so every transaction answers three questions at once: which account,
which restricted fund, which programme. It covers the full accounting cycle (chart of accounts →
journals → ledger → period close → reporting), the operational subsystems that feed it (procurement,
payables, receivables, payroll, fixed assets, bank reconciliation), and the donor-facing outputs
(fund statements, grant burn, budget variance, donor report packs).

Functional currency is KES. Reporting framework is IFRS (with the fund-accounting presentation
non-profits require: restricted / unrestricted / endowment fund balances rather than equity).

**Primary users and what they need from it**

| Role | Needs |
|---|---|
| Finance Officer | Post journals, capture bills, do bank rec, run payroll, close the period |
| Finance Manager | Approve journals and payment runs, monitor budget vs actual, sign off close |
| Executive Director | Approve procurement above threshold, fund transfers, disposals |
| Programme / budget holder | Raise requisitions, see own budget lines and burn |
| Grants Officer | Grant burn, donor reports, restricted-fund compliance |
| Auditor (read-only) | Ledger drill-down, audit trail, period-close evidence |

## About the design files

The files in this bundle are **design references created in HTML** — working prototypes that show
the intended layout, visual language and interaction behaviour. **They are not production code to
copy.** The prototype holds all data in memory in one component; there is no database, no auth, no
API, no persistence.

The task is to **recreate these designs in the target codebase's environment** using its established
patterns, component library, routing and data layer. If no codebase exists yet, choose an appropriate
stack (a server-rendered or SPA web app with a relational database — the domain is transactional and
integrity-critical, so PostgreSQL or equivalent, not a document store) and implement the designs
there.

Read the domain rules in this README as the specification. Read the HTML as the visual specification.
Where they disagree, the README wins — the prototype takes shortcuts the real system must not.

## Fidelity

**High-fidelity.** Colours, typography, spacing, density, states and copy are final and intentional.
Recreate the UI faithfully using the codebase's existing libraries. Two caveats:

- **Icons** are placeholder Unicode geometric glyphs (◧ ◷ ☰ ▤ ✎ ◇ ◆ ⊞ ⇄ ▣ ◫ ◔ ◈ ◉ ▦ ◐ ⌇ ◍ ⚙).
  Replace with a real icon set (Lucide, Phosphor, Material Symbols) keeping the same 14px optical size.
- **Data** is seeded and deterministic, generated by a seeded PRNG so the numbers articulate
  (assets − liabilities = funds; debit totals = credit totals). Real data replaces it, but the
  *articulation* is a hard requirement — see "Accounting integrity rules".

## Information architecture

Persistent left sidebar (236px, dark) + top bar (52px, white) + scrolling content area. Single-page
app; `page` state selects the screen. Sidebar groups:

**Overview** — Dashboard, Period close
**Accounting** — Chart of accounts, General ledger, Journals, Payables, Receivables, Procurement,
Bank reconciliation, Asset register, Asset verification, Payroll
**Funds and grants** — Funds, Grants and awards, Budgets, Donor reports
**Insight** — Cashflow forecast, Reports, Settings

Plus a separate **Login** screen (`ELOG Finance - Login.dc.html`).

Top bar carries: breadcrumb (group / page), **Entity switcher** (multi-entity: ELOG national office
and regional/project entities), **FY badge** (FY2026, Open/Closed indicator), **Notifications** bell
with unread count and a dropdown (tabs: All / Unread; grouped by day; kind label + timestamp +
title + body; mark-all-read), **User menu** (avatar with initials → profile drawer, preferences,
sign out with an unposted-drafts warning).

## Screens

### 1. Dashboard (`dash`) — "Finance overview"
**Purpose:** the 30-second answer to "are we solvent, on budget, and compliant?"
**Layout:** KPI row across the top, then a two-column grid (wider left column for charts/tables,
narrower right rail for attention items).
**Contents:** cash position by bank/M-Pesa account; unrestricted vs restricted split (the number
that actually matters for a non-profit — total cash is misleading when most of it is committed);
budget vs actual to date; grant burn by donor; items needing the user's action (journals awaiting
approval, requisitions to approve, unreconciled items, overdue bills, expiring grants).
**Behaviour:** every card is a link into the screen that owns the detail. Attention items are
role-filtered.

### 2. Period close (`period`)
**Purpose:** run and evidence the month-end close.
**Layout:** period selector, a vertical checklist of close steps with tick state, and an activity log.
**Close steps:** bank reconciled · M-Pesa reconciled · accruals posted · depreciation run · payroll
posted · management review · sign-off.
**Behaviour:** all steps must tick before **Close period** is enabled. Closing locks the period to
further posting. Reopening requires a reason and Finance Manager approval, and both actions append
to the immutable log (`what` + `meta` = timestamp · actor · approver). State seeds Jan–Jul 2026 as
closed, Aug 2026 open.

### 3. Chart of accounts (`coa`)
**Purpose:** maintain the account structure.
**Layout:** filter/search bar, hierarchical table (level 1 groups → level 2 → leaf accounts),
detail drawer on row click.
**Columns:** code, name, type (Asset / Liability / Fund / Income / Expense), normal balance
(Debit/Credit, derived — see rules), level, programme, status (Active / Inactive), balance.
**Behaviour:** expand/collapse hierarchy; only leaf accounts are postable; inactive accounts cannot
be selected in the journal editor; a leaf with movement cannot be deleted, only deactivated.

### 4. General ledger (`gl`)
**Purpose:** drill from a balance to the transactions behind it.
**Layout:** account selector + period / fund / programme / search filters; running-balance table.
**Columns:** date, reference, narration, programme, fund, debit, credit, running balance, source
document.
**Behaviour:** opening balance row, then movement, then closing — closing must equal the CoA balance.
Rows link to their source journal/bill/receipt. Filters compose.

### 5. Journals (`journals`)
**Purpose:** post and approve double-entry journals.
**Layout:** list (filter by status/type, search) + full journal editor.
**Statuses:** Draft → Awaiting approval → Posted (and Rejected, Reversed).
**Editor:** header (date, type, reference, narration, attachment) + line grid (account, description,
programme, fund, debit, credit) with live totals and an out-of-balance guard.
**Rules:** cannot submit unbalanced; cannot post to a closed period; cannot post to an inactive or
non-leaf account; **poster ≠ approver** (segregation of duties); posted journals are immutable —
correction is by reversal, which creates a linked contra journal.

### 6. Payables (`payables`)
**Purpose:** supplier bills through to payment.
**Layout:** ageing summary strip, bill list (filter: status / ageing bucket / fund, search,
multi-select), bill detail drawer.
**Ageing buckets:** current, 1–30, 31–60, 61–90, 90+.
**Behaviour:** three-way match against PO and GRN; approve for payment; batch-select into a payment
run; posting a payment clears the payable and hits the bank/M-Pesa account. Withholding tax and VAT
handled on the bill (Kenyan compliance).

### 7. Receivables (`receivables`)
**Purpose:** track amounts due to ELOG — mostly grant tranches and reimbursable claims, not trade sales.
**Layout:** mirror of Payables: ageing strip, invoice list (filter: status / fund / ageing, search,
multi-select), detail with receipt capture.
**Behaviour:** record receipt (full or partial) against an invoice; allocate to fund; post to bank.

### 8. Procurement (`procure`) — fully built end-to-end
**Purpose:** requisition → quotation → PO → goods received → bill, with the controls a donor audit expects.
**Layout:** view switcher (Requisitions / Quotations / Orders / Receipts), list with tabs
(Open / All / Mine), search, detail drawer per document, "New requisition" modal.
**Requisition lifecycle:** Draft → Submitted → Approved → RFQ issued → PO raised → Received → Billed
→ Closed (plus Rejected).
**Rules implemented:**
- Budget check on approval — approval is **blocked** if a line exceeds the remaining budget on its
  account × programme × fund combination.
- Three-quote rule — requisitions above the threshold are flagged and cannot proceed to PO without
  three quotations recorded (or a documented single-source waiver).
- PO raising commits the budget (commitment accounting: committed ≠ actual, both reduce available).
- GRN posting recognises the supplier payable and closes the requisition.
- Bill posting allocates to the correct cost centre, programme and fund.
- Every transition writes to the audit trail and posts to Journals where it has an accounting effect.
**New requisition form fields:** title, programme, fund, account code, need-by date, amount, lines.

### 9. Bank reconciliation (`bankrec`)
**Purpose:** match statement lines to book entries.
**Layout:** account + period selector, side-by-side panes (statement lines | book entries), match
tray, reconciliation summary.
**Behaviour:** select one-or-many on each side → **Match** (supports 1:1, 1:many, many:1);
matched pairs move to a posted list; unmatched statement lines can be posted as new journals
(bank charges, interest, direct debits). Summary must reconcile: statement closing balance =
book balance + unpresented − uncleared. Covers both bank accounts and M-Pesa paybill.

### 10. Asset register (`assets`)
**Purpose:** fixed assets, depreciation, disposals.
**Layout:** filter/search + register table, asset detail drawer, depreciation run panel, disposal modal.
**Columns:** tag, description, class, location, custodian, acquisition date, cost, funding source
(which grant bought it — donors often retain title), accumulated depreciation, NBV, status.
**Behaviour:** run depreciation for a period (posts a journal); record disposal (method, date,
proceeds, buyer, board minute reference, donor consent reference, reason) — disposal posts the
gain/loss journal and, where the asset was donor-funded, flags the consent requirement.

### 11. Asset verification (`verify`)
**Purpose:** physical verification counts against the register.
**Layout:** location selector, filter (All / Verified / Not found / Condition issue), results list.
**Behaviour:** per-asset outcome capture with condition note; produces an exceptions report;
unresolved exceptions feed the audit trail. *(Thinnest module — see "Known gaps".)*

### 12. Payroll (`payroll`)
**Purpose:** monthly payroll run with statutory deductions and programme allocation.
**Layout:** period selector, staff roster list (filter / search), staff detail, run summary,
approval action. Animated period swap (see Interactions).
**Earnings:** basic, house allowance, transport allowance, acting allowance — pro-rated by portion
of month worked (joiners and leavers move the roster month to month).
**Deductions:** PAYE, NSSF, SHIF/NHIF, housing levy, staff advances/loans.
**Allocation:** each staff cost splits across programmes and funds by an allocation percentage;
allocation must total 100% and the last line absorbs the rounding residual.
**Behaviour:** period must be open; run → review → approve → post (posts a journal per programme/fund
allocation). Jan–Jul 2026 seeded as posted.

### 13. Funds (`funds`)
**Purpose:** the fund-accounting core — balance and movement per restricted fund.
**Layout:** filter/search, fund list, fund detail (opening balance, income, expenditure, transfers,
closing balance), transfer modal.
**Fund types:** unrestricted (General), restricted (per grant/donor), designated (Capital),
endowment (capital fixed by trust deed).
**Behaviour:** inter-fund transfer requires from/to, amount, board minute reference and reason, and
posts a balanced pair of entries. **A restricted fund can never go negative** — that is
over-spending a donor's money and must be blocked, not warned.

### 14. Grants and awards (`grants`)
**Purpose:** grant lifecycle and burn.
**Layout:** filter/search, grant list, grant detail.
**Detail:** donor, award reference, agreement value, currency, period, budget lines, spent to date,
committed, remaining, burn rate vs elapsed time, reporting calendar and next report due, eligible
cost rules, retention/holdback.
**Behaviour:** flags over/under-burn against elapsed period and grants approaching expiry with
unspent balance.

### 15. Budgets (`budgets`)
**Purpose:** budget vs actual with versioning.
**Layout:** version selector (FY2026 Original / Revision 1 (approved) / Revision 2 (working)),
grouping selector (Account group / Programme / Fund), basis selector (phasing), search, variance
table, line detail drawer.
**Columns:** line, annual budget, phased budget to date, actual, committed, variance, variance %.
**Phasing profiles:** even, front-loaded, back-loaded, event-driven (election cycles are spiky —
phasing matters, straight 1/12 would misreport every month).
**Behaviour:** only one approved version at a time; a working revision can be edited and submitted
for approval; approved budgets drive the procurement budget check.

### 16. Donor reports (`donor`)
**Purpose:** generate the report pack each donor's agreement requires.
**Layout:** donor/grant selector, report period, pack contents checklist, preview, export.
**Contents:** fund statement, expenditure against budget lines, narrative placeholders, supporting
schedules, variance explanations.
**Behaviour:** report is generated from posted transactions only; a period that is not closed is
labelled provisional.

### 17. Cashflow forecast (`cashflow`)
**Purpose:** will we be able to pay staff in three months?
**Layout:** scenario selector (Base case / Delayed tranche / Grant lost), hold toggle, forecast
table + chart by month.
**Rows:** opening cash, expected grant receipts (by probability), payroll, operating costs,
committed procurement, closing cash, of which unrestricted.
**Behaviour:** scenarios re-run the projection; the unrestricted line is the real liquidity signal.

### 18. Reports (`reports`)
**Purpose:** statutory and management reporting.
**Contents:** trial balance, statement of financial position, statement of income and expenditure
(by fund), statement of changes in fund balances, cashflow statement, fund statements,
budget variance, ageing reports, asset register, audit trail export.
**Behaviour:** period and entity scoped; export to PDF/Excel; each report states its basis and
whether the period is closed.

### 19. Settings (`settings`)
**Purpose:** configuration.
**Contents:** entities, fiscal year and period calendar, currencies and rates, users and roles,
approval thresholds and delegation-of-authority limits, account defaults, tax rates, numbering
sequences, notification preferences.

### 20. Login (`ELOG Finance - Login.dc.html`)
Separate file. Email + password, organisation branding, error state, forgotten-password link.
Real implementation needs MFA — see "Security".

## Accounting integrity rules (non-negotiable)

These are the rules the prototype encodes and the real system must enforce at the **database and
service layer**, not just the UI:

1. **Every journal balances.** Sum of debits = sum of credits, to the minor unit. Reject otherwise.
2. **Normal balance is derived, not stored:** Asset and Expense are debit-normal; Liability, Fund and
   Income are credit-normal; **contra accounts invert** — an account whose name matches
   *accumulated depreciation / provision for / allowance for / impairment* takes the opposite normal
   balance. (Prototype: `CONTRA_RX` + `NORMAL()`.)
3. **The statements articulate.** Assets − Liabilities = Fund balances. Surplus/deficit
   (Income − Expense) flows to the current-year fund account (3900). Debit-normal totals =
   credit-normal totals.
4. **Posted is immutable.** No edit, no delete. Correction is a linked reversal journal.
5. **Closed periods are locked.** No posting, no back-dating. Reopening is an approved, logged event.
6. **Segregation of duties.** Preparer ≠ approver on journals, payment runs, payroll and procurement.
7. **Three-dimensional coding.** Every posting line carries account + fund + programme. No exceptions,
   no default-and-forget.
8. **Restricted funds cannot go negative.** Hard block.
9. **Commitment accounting.** Available budget = approved budget − actual − committed (open POs).
10. **Full audit trail.** Every state transition records actor, timestamp, before/after and reason
    where applicable. Append-only, exportable.

## Interactions and behaviour

- **Navigation:** sidebar click sets `page`. Active item: `#1B3A32` background, white text,
  `inset 2px 0 0 #1FA37E` left marker, weight 600. Idle: transparent, `#B9C6C0`; hover
  `#152925` background, `#F2F5F3` text.
- **Drawers** (record detail): fixed right, 432px wide (`max-width:92vw`), white, left border
  `#E4E2DB`, shadow `-18px 0 40px rgba(13,27,24,0.14)`, scrim `rgba(13,27,24,0.28)`.
  Animation: `drawerIn` — `translateX(24px)` → none with opacity 0 → 1, 200ms ease.
  Scrim fades in 140ms. Click-scrim or × closes.
- **Dropdowns** (notifications 392px, user menu 268px): absolute, `top:38px; right:0`, white,
  1px `#E4E2DB`, radius 9px, shadow `0 12px 30px rgba(13,27,24,0.13)`, `fadeIn` 130ms ease.
  A transparent fixed overlay behind them catches outside clicks.
- **Payroll period swap:** directional slide+fade — `prSwapA/prSwapB` (from `translateY(10px)`)
  and `prSwapUpA/prSwapUpB` (from `translateY(-10px)`) alternate between two keyframe names so a
  repeated swap in the same direction re-triggers the animation. Direction depends on whether the
  new period is later or earlier.
- **Tables:** header row is uppercase 9.5–11px, letter-spacing 0.05–0.1em, `#8B948F`. Numeric cells
  right-aligned in IBM Plex Mono. Row hover `#F4F2ED`. Zero renders as an em dash `—`; negatives
  render in parentheses, not with a minus sign (accounting convention).
- **Multi-select:** checkbox column, selection count + bulk action bar appears when ≥1 selected.
- **Empty states:** centred 12px `#8B948F` sentence, plain language ("Nothing unread. You're caught
  up.") — never an illustration.
- **Destructive/blocked actions:** stated reason, not a generic error. e.g. budget-blocked approval
  names the line, the account and the shortfall.
- **Sign out:** confirm step that reports the user's unposted draft count.
- **Responsive:** designed for desktop ≥1280px. Below that, collapse the sidebar to icons; drawers
  go full-width. The dense tables are not a mobile experience — treat mobile as out of scope unless
  the requirement is explicit (a field-verification mobile view for asset counts is the one
  plausible exception).

## State management

The prototype keeps everything in one component's `state`. In production, split by concern:

**Server state (fetched, cached, invalidated):** chart of accounts, journals, ledger, bills,
invoices, requisitions/POs/GRNs, assets, payroll runs, funds, grants, budgets, bank statements,
notifications, current user + permissions, entity list, period status.

**UI state (client-only):** `page` (→ route), active filters/search per screen, selected row / open
drawer, open modal, multi-select sets, dropdown open flags, form drafts, animation direction.

Prototype state keys worth mirroring as route/query params so views are linkable and shareable:
`page`, `glAccount`, `glPeriod`, `glFund`, `glProgram`, `jFilter`/`jType`, `apFilter`/`apAge`/`apFund`,
`arTab`/`arAge`/`arFund`, `pqView`/`pqTab`, `brAcct`/`brPeriod`, `prPeriod`, `pcPeriod`,
`bVersion`/`bGroup`/`bBasis`, `asFilter`, `avLocation`/`avFilter`, `entity`, fiscal year.

**Data fetching:** all list screens need server-side filtering, sorting and pagination — the ledger
and journal tables will reach hundreds of thousands of rows. Do not port the prototype's
filter-in-memory approach. Totals and ageing summaries must be computed server-side over the whole
filtered set, not the current page.

**Mutations:** every posting action is a transaction. Journal posting, payment runs, payroll posting,
depreciation runs, GRN posting and period close must be atomic and idempotent (a retried request must
not double-post). Use an idempotency key per submission.

## Security and compliance

- **Auth:** email + password with MFA mandatory for anyone who can approve or post. Session timeout.
- **Authorisation:** role-based, enforced server-side per action, not by hiding buttons. Approval
  limits are data (`approval_limit`), not code.
- **Audit:** append-only `audit_event` table, no application-level delete. Retain per donor
  agreement (typically 7 years).
- **Data residency and privacy:** payroll and staff data is personal data — Kenya's Data Protection
  Act 2019 applies. Restrict access, log reads of payroll records.
- **Attachments:** every bill, requisition, journal and disposal supports document attachment;
  donor audits ask for the source document, not the entry.
- **Backups:** point-in-time recovery. A finance ledger with no restore path is a liability.

## Known gaps in the prototype

Things the real build must add — the prototype either stubs or omits them:

1. **Asset verification** is the thinnest module; the count workflow needs a proper round →
   assignment → capture → exception → resolution lifecycle (and probably a mobile capture view).
2. **Partial receipts and partial payments** — procurement assumes clean full receipt.
3. **Credit notes, debit notes, supplier returns.**
4. **Multi-currency** — grants arrive in USD/EUR. FX revaluation, realised/unrealised gains, and
   rate-at-transaction vs rate-at-reporting are not modelled.
5. **Delegation of authority** when an approver is on leave.
6. **Contract retention and staged payments** for construction/consultancy.
7. **Recurring journals and accrual reversals.**
8. **Grant sub-recipient / downstream partner accounting** — common in this sector.
9. **Notification delivery** (email/SMS digest) — the bell is in-app only.
10. **Bulk import** — opening balances, bank statement files (CSV/MT940), staff data.
